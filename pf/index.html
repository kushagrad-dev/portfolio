CASE STUDY · 01

From a vague feature idea to a focused engineering scope.

How I used AI to challenge assumptions, identify implementation risks, and turn a broad feature request into a small, implementable first version.

THE TARGET

Scope a meal-swap suggestions feature for a hostel nutrition and macro tracker.

Users already log meals and track their personal protein target. The feature should suggest items from today's remaining menu that can help close the user's remaining protein gap.

V0 · NAIVE PROMPT

My starting point was a simple request for ideas for building the feature.

The response was broad and introduced possibilities such as external food APIs and machine-learning approaches that were not necessary for the first version.

V2 · REAL CONTEXT

Adding the actual project context changed the quality of the discussion significantly.

The existing stack was Next.js, Node/Express and MongoDB. The menu was already structured in the database, and the feature only needed to work with the existing day's menu.

This reframed the problem as ranking a small fixed set of existing items rather than building a new recommendation system.

PROMPT ITERATION

I iterated through multiple versions of the prompt instead of accepting the first answer.

  • V1: assigned AI a collaborative role and made the constraints explicit.
  • V2: added real project context and narrowed the problem.
  • V3: used examples to improve the output format and reusability.
  • V4: required a concrete output structure and edge cases.
  • V5: decomposed the problem into implementation steps and surfaced data-flow risks.
RISKS SURFACED

Step decomposition surfaced questions that needed to be answered before implementation.

  • Does every menu item have a usable protein value?
  • How is the user's remaining menu determined?
  • Where is the daily protein target stored or calculated?
  • How do we avoid calculating the same target twice?
FINAL CONSTRAINTS
  • Use existing structured menu data.
  • Focus on the protein gap.
  • No external nutrition API.
  • No new recommendation or ML pipeline.
  • No new database collections.
  • Keep the first version small and implementable.
FINAL DECISION

The final scope was a simple suggestion endpoint:

GET /api/suggestions?userId=&date=

The endpoint returns the user's remaining protein gap and ranked suggestions from the remaining menu items.

EDGE CASES
  • Missing protein target.
  • Protein target already met.
  • Local date/time handling.
  • Menu items missing protein data.
WHAT MOVED THE NEEDLE

The biggest improvement came from adding real context, followed by forcing the reasoning into steps and explicitly considering edge cases.

Few-shot examples and role assignment helped, but they had less impact than understanding the actual engineering constraints.

MY DECISION

AI helped me explore the problem, identify risks, and challenge the scope. I retained the final decision about what should actually be built.

The goal was not to make the solution as sophisticated as possible. It was to make the first version useful, understandable, and implementable within the existing system.
